# 学习路线一致性审查清单

交付前（及用户要求复查时）逐项核对。审查基准 = 用户目标 + 已确认约束（自包含、零链接、认知顺序、纯目标技术视角）。
**审查阶段只读不改**：输出分级报告，经用户确认后再修复。

## A. 结构与顺序

- [ ] **无"先用后教"**：任何示例/练习中出现的语法、包、特性，必须在它首次被使用的位置之前已正式讲授
  - 典型事故：context 示例用了还没讲的 select/channel（context 应排在并发基础之后）
  - 检查法：对每个"进阶特性"章节，列出其代码依赖的前置知识点，逐一确认已前置
- [ ] 无法前置的小依赖（如 io.ReadAll、bytes.NewReader）：要么加一句"混个脸熟"的说明，要么前移
- [ ] 阶段划分符合认知递进，没有退化成照搬源教程目录

## B. 内容一致性

- [ ] **练习不超纲**：每道练习所需的全部知识均已讲授
  - 典型事故：爬虫练习需要 http.Get 但正文没教；Top N 项目需要排序但没教 sort；CLI 项目需要 os.Args 但没教
  - 检查法：逐题列出依赖 API，反查正文是否覆盖
- [ ] **承诺必兑现**：所有"阶段 X 会讲到 / 会接入"的伏笔都真实兑现
  - 典型事故：说"Gin 里用 c.Request.Context()，阶段九可直接接入"，但阶段九代码里根本没用 context
- [ ] **自检全覆盖**：每个新增小节都有对应的过关自检问题（不能只有老章节有）
- [ ] 正文零链接、零"参见官网某页"式指引
- [ ] 代码示例语法正确、可运行；风格统一（Go 场景缩进用 tab；注释解释"为什么"而不只是"是什么"）

## C. 声明与事实一致

- [ ] **时长符体量**：头部总时长与实际内容量匹配；内容大幅扩充后必须回头更新时长声明
- [ ] **版本基线**：明确声明按哪个版本撰写（如 Go 1.22+）；受版本影响的行为差异要标注（如循环变量捕获在 Go 1.22 已修复、仅旧版存在）
- [ ] 配置示例（go.mod 等）与声明的版本基线一致

## D. 范围控制

- [ ] 目标范围内全覆盖：对照该技术的官方知识清单（spec/文档目录）盘点缺口
- [ ] 缺口分级处理：练习需要但未教（必须补正文）/ 工程常用件（建议补正文）/ 进阶主题（只进附录）
- [ ] 超出目标的内容（性能调优、部署运维等）只出现在附录或"学完之后的方向"，不混入正文
- [ ] 无用户未要求的跨语言对照残留

## E. 毕业项目检查

- [ ] 至少一个项目衔接真实工程形态（数据库 / Web API / 并发服务）
- [ ] 项目所需技能全部在正文中，且能串联大部分阶段所学

## 问题分级与修复

| 级别 | 定义 | 处理 |
|---|---|---|
| 🔴 结构硬伤 | 先用后教、承诺悬空、练习超纲 | 必修 |
| 🟡 执行偏差 | 自检缺口、声明失真、版本混淆 | 建议修 |
| 🟢 小瑕疵 | 未介绍即用的小函数、措辞不一致 | 视情况修 |

**修复时的连带检查**（移动/增删章节后）：
- 全文 grep 被移动小节的名称，更新所有"第 N 节""阶段 X"式交叉引用
- 重新编号受影响的小节标题
- 同步迁移该小节的自检问题到新位置
- 若小节支撑阶段目标句（如"用 context 管理超时"），阶段目标句也要同步更新
